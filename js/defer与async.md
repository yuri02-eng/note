### **`defer` 与 `async` 属性系统学习笔记**

![三种脚本加载方法的工作原理：默认情况下，在获取和执行 JavaScript 时，解析过程被阻塞。使用 async 时，解析暂停，仅执行。使用 defer 时，解析不会暂停，但在解析完所有其他内容后才开始执行](https://developer.mozilla.org/zh-CN/docs/Web/HTML/Reference/Elements/script/async-defer.jpg)

使用了 **`async`** 属性加载的脚本不会在下载时阻塞页面。这意味着在脚本执行完成之前，将无法为用户处理和渲染网页上的其余内容。无法保证脚本的运行次序。当页面的脚本之间彼此独立，且不依赖于本页面的其他任何脚本时，`async` 是最理想的选择。

使用 `defer` 属性加载的脚本将按照它们在页面上出现的顺序加载。在页面内容全部加载完毕之前，脚本不会运行，如果脚本依赖于 DOM 的存在（例如，脚本修改了页面上的一个或多个元素），这一点非常有用。

#### **一、核心问题：默认的脚本加载行为（阻塞解析）**

浏览器解析和渲染 HTML 的过程是线性的。当解析器遇到一个普通的 `<script>` 标签时，它会立即执行以下步骤，这个过程是**同步**的：

1.  **停止解析（Block Parsing）**：暂停 HTML 文档的解析。
2.  **下载脚本（Fetch Script）**：发起网络请求以下载外部脚本文件（如果是内联脚本则跳过此步）。
3.  **执行脚本（Execute Script）**：立即执行下载完成或内联的 JavaScript 代码。
4.  **继续解析（Resume Parsing）**：脚本执行完毕后，恢复 HTML 文档的解析。

**带来的问题**：如果脚本文件很大或网络条件很差，用户会长时间面对一个**空白页面（白屏）**，导致极差的用户体验。脚本成为了页面渲染的“阻塞点”。

---

#### **二、解决方案：异步加载 (`defer` & `async`)**

`defer` 和 `async` 都是为了解决上述阻塞问题而生的属性。它们都让浏览器**异步地**加载外部脚本，即在后台下载脚本的同时，HTML 解析器可以继续工作。

**核心共同点**：**脚本的下载过程都不会阻塞 HTML 解析**。

**根本不同点**：**脚本的执行时机和顺序**。

---

#### **三、`defer` (延迟执行)**

*   **行为模式**：
    1.  **异步下载**：浏览器在后台开始下载脚本，同时 HTML 解析继续。
    2.  **延迟执行**：即使脚本很快下载完成，它也会**等待**。
    3.  **执行时机**：脚本的执行被**延迟**到**整个 HTML 文档完全被解析和构建（DOM 树准备就绪）之后**，但在 `DOMContentLoaded` 事件触发**之前**。
    4.  **顺序保证**：多个带有 `defer` 的脚本会**严格按照它们在 HTML 中出现的顺序执行**。这是浏览器保证的。

*   **优点**：
    *   完全不阻塞页面渲染。
    *   保证执行顺序，适合有依赖关系的脚本。
    *   执行时 DOM 已 100% 构建完成，可以安全地进行 DOM 操作。

*   **代码示例**：
    ```html
    <script src="library.js" defer></script> <!-- 先执行 -->
    <script src="app.js" defer></script>     <!-- 后执行，能安全使用 library.js -->
    ```

*   **流程图解**：
    ```
    HTML Parsing (构建DOM)
    ↓
    → [defer script 1] 开始下载 → 下载完成 → (等待)
    → [defer script 2] 开始下载 → 下载完成 → (等待)
    ↓
    HTML 解析完成 (DOM Ready)
    ↓
    按顺序执行所有 defer 脚本
    ↓
    触发 DOMContentLoaded 事件
    ```

---

#### **四、`async` (异步执行)**

*   **行为模式**：
    1.  **异步下载**：浏览器在后台开始下载脚本，同时 HTML 解析继续。
    2.  **尽快执行**：脚本一旦下载完成，HTML 解析会**被立即暂停**，以便**尽快执行**该脚本。
    3.  **执行时机**：**下载完成后立即执行**。执行时机无法预测，可能在 HTML 解析完成之前或之后。
    4.  **顺序无保证**：多个 `async` 脚本的**执行顺序完全由下载完成的先后顺序决定**（“加载优先”顺序）。先下载完的先执行，与声明顺序无关。

*   **优点**：
    *   下载不阻塞渲染。
    *   能让脚本尽快得到执行。

*   **缺点**：
    *   执行时会阻塞 HTML 解析。
    *   执行顺序无法控制，不适合有依赖关系的脚本。
    *   执行时 DOM 可能尚未完全构建，操作 DOM 有风险。

*   **代码示例**：
    ```html
    <script src="analytics.js" async></script> <!-- 独立的统计脚本 -->
    <script src="advertisement.js" async></script> <!-- 独立的广告脚本 -->
    <!-- 这两个脚本谁先执行都可以，互不影响 -->
    ```

*   **流程图解**：
    ```
    HTML Parsing (构建DOM)
    ↓
    → [async script 1] 开始下载 → 下载完成 → (暂停解析) → 执行脚本1 → (恢复解析)
    → [async script 2] 开始下载 → 下载完成 → (暂停解析) → 执行脚本2 → (恢复解析)
    ↓
    HTML 解析完成 (DOM Ready)
    ↓
    触发 DOMContentLoaded 事件 (可能在 async 脚本执行前或后触发)
    ```

#### **五、对比总结表**

| 特性 | `<script>` (默认) | `<script defer>` | `<script async>` |
| :--- | :--- | :--- | :--- |
| **加载是否阻塞解析** | **是** | **否** (异步加载) | **否** (异步加载) |
| **执行是否阻塞解析** | **是** | **否** (延迟执行) | **是** (下载完即执行) |
| **执行时机** | 下载完成后立即 | DOM 构建完成后，`DOMContentLoaded` 前 | 下载完成后立即 (无法预测) |
| **执行顺序** | 按书写顺序 | **严格按书写顺序** | **按下载完成顺序** (无法保证) |
| **DOM 就绪保证** | 不确定 | **是** | **否** |
| **典型用例** | 极少数需立即执行的脚本 | **绝大多数需要操作 DOM 或有依赖的脚本** | 完全独立的第三方脚本 (分析、广告) |

---

#### **六、最佳实践与注意事项**

1.  **优先使用 `defer`**：对于你自己编写的、需要操作 DOM 或存在依赖关系的脚本，`defer` 是最安全、最有效的选择。它兼具了不阻塞渲染和保证执行顺序两大优点。

2.  **`async` 用于独立脚本**：将 `async` 用于那些“锦上添花”的、完全独立的第三方脚本，如数据分析（Google Analytics）、广告投放等。它们的执行不应影响你主要应用的功能。

3.  **模块脚本 (`type="module"`) 的默认行为**：
    *   原生的 ES6 模块（`<script type="module">`）默认具有 `defer` 的行为。
    *   你仍然可以给模块脚本添加 `async` 属性，使其在下载完成后立即执行，并且不等待其他模块。例如：`<script type="module" async>`。

4.  **`DOMContentLoaded` 事件**：
    *   `defer` 脚本的执行肯定在 `DOMContentLoaded` 事件之前完成。
    *   `async` 脚本可能在任何时候执行，因此它可能在 `DOMContentLoaded` 之前或之后触发。

5.  **不要同时使用 `defer` 和 `async`**：
    *   在现代浏览器中，如果同时指定 `defer` 和 `async`，`async` 会优先生效。
    *   为了代码清晰和避免旧浏览器兼容性问题，应只选择其中一个使用
