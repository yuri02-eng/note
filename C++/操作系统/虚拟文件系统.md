# Linux虚拟文件系统（VFS）详解

在Linux系统中，用户和应用程序通过**文件系统**与存储设备、网络资源或其他I/O设备交互。然而，Linux支持的文件系统种类繁多——从本地磁盘文件系统（如ext4、XFS）到网络文件系统（如NFS、CIFS），再到内存文件系统（如tmpfs）和伪文件系统（如proc、sysfs）。

如何让这些差异巨大的文件系统对外提供统一的接口？**虚拟文件系统（Virtual File System，VFS）** 正是解决这一问题的核心抽象层。

![img](https://i-blog.csdnimg.cn/direct/cc4b307047db4811b045d379b918b7ed.png)

1. **向上**：为用户空间提供统一的文件操作接口（如POSIX标准的`open`、`read`）；
2. **向下**：定义文件系统驱动需实现的接口规范（如`super_block`、`inode_operations`），并通过`file_system_type`结构体注册文件系统类型（如`ext4_fs_type`）。

VFS的本质是Linux内核中的一个“中间层”，它定义了一套统一的文件操作接口规范，屏蔽了底层不同文件系统的实现细节。用户空间的应用程序通过标准系统调用（如`open`、`read`、`write`）与VFS交互，VFS再将请求转发给具体的文件系统驱动。这种设计不仅简化了应用程序的开发（无需适配不同文件系统），也为内核支持新文件系统提供了灵活性。

## 1. VFS核心概念

### 1.1 超级块（Superblock）[#](https://geek-blogs.com/blog/linux-virtual-filesystem/#11-chao1-ji2-kuai4-superblock)

### 作用（Why it exists）

`super_block` 的核心作用是：

> **在内核中表示“一个已经挂载的文件系统实例”**

它解决的问题是：

* 内核需要知道：

  * 这是 **什么文件系统**（ext4 / xfs / proc / tmpfs）
  * 这个文件系统 **有多大**
  * **块大小是多少**
  * **根目录从哪里开始**
* 并且这些信息要：

  * **在 mount 时一次性读取**
  * **在整个挂载周期内复用**

📌 **一句话总结**

> `super_block` 负责回答：**“我现在挂的是哪一个文件系统？”**

---

# 1.2 `struct inode` —— 文件的“真实身份”

### 作用（Why it exists）

`inode` 的核心作用是：

> **唯一标识并描述一个文件或目录的本体**

它解决的问题是：

* 文件系统需要：

  * 存储文件元数据
  * 定位文件内容所在的数据块
* 同时支持：

  * 硬链接（多个名字 → 同一个 inode）
  * 文件名与文件内容解耦

📌 **一句话总结**

> `inode` 负责回答：**“这个文件到底是什么？”**

---

# 1.3 `struct dentry` —— 路径解析与缓存加速器

### 作用（Why it exists）

`dentry` 的核心作用是：

> **将“路径名”映射到 inode，并缓存该结果**

它解决的问题是：

* 路径解析是高频操作（open/stat/access）
* 每次都从磁盘查找目录结构会极慢
* 需要：

  * 快速判断路径是否存在
  * 快速定位 inode

📌 **一句话总结**

> `dentry` 负责回答：**“这个名字指向哪个 inode？”**

---

# 1.4 `struct file` —— 一次“打开行为”的上下文

### 作用（Why it exists）

`file` 的核心作用是：

> **描述进程“如何”使用一个文件**

它解决的问题是：

* 同一个文件可能被：

  * 多个进程打开
  * 以不同模式打开
* 每个打开行为需要：

  * 独立的文件偏移
  * 独立的访问标志

📌 **一句话总结**

> `file` 负责回答：**“这次打开，进程要怎么用这个文件？”**

---

# 1.5 `struct file_operations` —— 行为抽象层

### 作用（Why it exists）

`file_operations` 的核心作用是：

> **定义“对文件能做什么，以及具体怎么做”**

它解决的问题是：

* VFS 需要统一接口（read/write/open）
* 不同文件系统实现完全不同
* 设备文件、proc、socket 行为也不同

📌 **一句话总结**

> `file_operations` 负责回答：**“这些操作具体由谁来实现？”**

# 最终：VFS 五大对象“责任划分表”

| 对象              | 关注点    | 解决的问题       |
| --------------- | ------ | ----------- |
| super_block     | 文件系统整体 | 我挂载的是什么文件系统 |
| inode           | 文件本体   | 文件是什么、在哪里   |
| dentry          | 名字与路径  | 名字指向谁       |
| file            | 打开实例   | 这次怎么用       |
| file_operations | 行为实现   | 操作如何执行      |

## 二、open() 系统调用：五大结构体如何“搭起来”

### 1️⃣ 用户态 → 内核态

```c
int fd = open("/home/user/a.txt", O_WRONLY | O_CREAT);
```

进入内核后：

```
sys_open
 └── do_sys_open
     └── do_filp_open
         └── path_openat
```

📌 **此时还没有 struct file**

------

### 2️⃣ 路径解析：dentry + inode 登场

#### 路径 `/home/user/a.txt` 被逐级解析：

```
/        → dentry("/")
home     → dentry("home")
user     → dentry("user")
a.txt    → dentry("a.txt")
```

涉及的核心逻辑：

```
path_lookupat
 └── link_path_walk
     └── lookup_fast / lookup_slow
```

📌 **这一阶段的主角**

| 结构体      | 作用               |
| ----------- | ------------------ |
| super_block | 提供文件系统上下文 |
| dentry      | 路径名缓存与查找   |
| inode       | 文件的元数据与定位 |

✅ 若文件存在
→ `dentry->d_inode != NULL`

❌ 若文件不存在 + O_CREAT
→ 创建 inode，并绑定到 dentry

------

### 3️⃣ inode 准备就绪

此时你已经得到：

```c
struct inode *inode;
```

它包含：

- 文件类型 / 权限
- 数据块位置
- **inode->i_fop（默认 file_operations）**

📌 **注意：inode 仍然不是“打开状态”**

------

### 4️⃣ 创建 struct file（关键一步）

```c
struct file *file = alloc_file();
```

初始化关键字段：

```c
file->f_inode = inode;
file->f_op    = inode->i_fop;
file->f_pos   = 0;
file->f_flags = O_WRONLY | O_CREAT;
```

📌 **struct file = “一次打开行为”**

------

### 5️⃣ 调用文件系统的 open 方法（若存在）

```c
file->f_op->open(inode, file);
```

- ext4 / proc / char device 可在此：
  - 替换 f_op
  - 初始化私有数据

------

### 6️⃣ 分配 FD，返回用户态

```c
fd = alloc_fd();
files_struct[fd] = file;
```

📌 至此：

```
FD → struct file → inode → super_block
                → file_operations
                → dentry（通过 path）
```

✅ **open() 完成**

------

## 二、write() 系统调用：数据如何真正写入

### 1️⃣ 用户态 → 内核态

```c
write(fd, buf, 4096);
```

进入内核：

```
sys_write
 └── ksys_write
     └── vfs_write
```

------

### 2️⃣ 通过 FD 找到 struct file

```c
struct file *file = current->files->fdt[fd];
```

📌 **关键点**

- write **完全不关心路径**
- 也不再查 dentry
- 一切从 `struct file` 开始

------

### 3️⃣ 权限与状态检查

```c
if (!(file->f_mode & FMODE_WRITE))
    return -EBADF;
```

------

### 4️⃣ 调用 file_operations->write

```c
file->f_op->write(file, buf, count, &file->f_pos);
```

📌 **VFS 在这里“停手”**

从这一刻起：

- ext4_write_iter
- procfs_write
- char_dev_write

由 **具体文件系统/设备决定**

------

### 5️⃣ ext4 为例（简化）

```
ext4_file_write_iter
 └── generic_file_write_iter
     └── page cache
         └── block mapping
             └── disk I/O
```

- 使用 inode 定位数据块
- 更新 inode->i_size
- 推进 file->f_pos

------

### 6️⃣ 返回写入字节数

```c
return bytes_written;
```

------

## 三、五大结构体在 open → write 中的“角色快照”

### 1️⃣ open() 阶段（创建 & 绑定）

| 结构体          | 状态                     |
| --------------- | ------------------------ |
| super_block     | 已存在，提供文件系统信息 |
| dentry          | 用于路径解析             |
| inode           | 查找 / 创建              |
| file            | **新创建**               |
| file_operations | 从 inode 复制到 file     |

------

### 2️⃣ write() 阶段（执行 & 更新）

| 结构体          | 是否参与                    |
| --------------- | --------------------------- |
| super_block     | 间接参与（块大小、FS 信息） |
| dentry          | ❌ 不参与                    |
| inode           | ✔️ 数据定位、元数据更新      |
| file            | ✔️ 文件偏移、状态            |
| file_operations | ✔️ write 实现                |

------

## 四、一句话总串联

> **open() 的本质**：
> 👉 *通过 dentry 找 inode，通过 inode 创建 file*

> **write() 的本质**：
> 👉 *通过 file 找操作方法，通过 inode 找数据位置*
