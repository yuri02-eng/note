# C 语言结构体内存对齐笔记（从硬件到 ABI 到 struct）

## 1. 什么是“对齐（alignment）”？

* 每种类型 `T` 都有一个对齐值（对齐要求），记作 `A(T)`。
* **对齐值为 N 的意思**：该类型对象的起始地址应当是 **N 的倍数**。
  例如 `double` 常见 `A(double)=8`，则 `double` 变量地址通常满足 `addr % 8 == 0`。

常见 64 位平台上（仅作典型例子，具体以平台/ABI 为准）：

* `A(char)=1`
* `A(int)=4`
* `A(double)=8`

### 对齐为何存在（直观原因）

* 硬件/CPU 在实现 load/store（读写）、原子操作、缓存访问时，**对齐的地址更容易、更快**处理。
* 有的架构对未对齐访问只是变慢；有的架构可能直接异常（fault）。

---

### 1.1 不对齐会带来什么“问题”？

#### 问题 A：可能需要两次访问 + 拼接（慢）

比如要读 4 字节，从地址 `1006` 开始读 `[1006..1009]`。
 但硬件一次更方便读的是对齐的 4 字节块：

- 块1 `[1004..1007]`
- 块2 `[1008..1011]`

你的数据跨了块边界，那硬件就得：

1. 读块1
2. 读块2
3. 把你要的那 4 字节拼起来

这就是“未对齐访问更慢”的本质：**更多内存事务/更多硬件逻辑**。

#### 问题 B：早期/很多 RISC 机器上甚至直接“不允许”（会异常）

为了省晶体管、简化流水线，很多架构干脆规定：

> 读 4 字节必须 4 对齐，不然就是对齐异常（alignment fault / bus error）。

这不是后来才发现问题再修补，而是：**硬件设计时就做出的取舍**：要么电路更复杂（支持任意地址），要么软件遵守规则（对齐）。

#### 问题 C：原子性与一致性也更麻烦

比如你想做一个“原子 8 字节读写”（很多平台要求地址 8 对齐）。
 如果不对齐、还跨了两个 cache line，硬件要保证“别的核心看不到一半新一半旧”，难度和成本会上升。

## 2. struct 是什么？它是不是“新类型”？

是的。`struct S` 本质上就是一个**新定义的数据类型**，类似 `int`、`double` 一样，拥有：

* **大小**：`sizeof(struct S)`
* **对齐**：`A(struct S)`（可用 C11 的 `alignof` 或 `_Alignof` 获取）

结构体的“新类型属性”并不是你手动写死的，而是由：

* 结构体成员的类型对齐需求
* 平台 ABI 的布局规则
  共同推导出来的。

---

## 3. “最大对齐”到底是什么？

对结构体 `struct S`，在常见 ABI 下通常遵循：

> **`A(struct S) = max( A(每个成员类型) )`**

也就是说：**结构体这个类型的对齐要求，等于它所有成员里对齐要求最大的那个。**

因此，“结构体按最大对齐”更精确的表述是：

* ✅ **结构体对齐值 = 最大成员的对齐值**
* ✅ **结构体对象地址必须是该对齐值的倍数**

> 注意：这并不意味着“每个成员都按最大对齐摆放”。
> 成员只需要满足**自己的对齐**即可。

---

## 4. 为什么还要让 `sizeof(struct)` 补齐到最大对齐的倍数？

除了 `A(struct S)`，ABI/编译器还会通常保证：

> **`sizeof(struct S)` 是 `A(struct S)` 的整数倍**

核心目的：**保证数组中的每个元素都对齐**。

如果 `struct S arr[N];`，数组元素起始地址为：

* `&arr[i] = &arr[0] + i * sizeof(struct S)`

若 `sizeof(struct S)` 不是 `A(struct S)` 的整数倍，就可能出现：

* `arr[0]` 起始对齐
* 但 `arr[1]` 起始错位，从而导致里面对齐要求最大的成员（如 `double`）不对齐

所以编译器会在结构体末尾加 **尾部 padding**，把 `sizeof(struct)` 补到对齐倍数。

---

## 5. 例子：为什么这个 struct 可能变成 16？

```c
struct S { double a; int b; char c; };
```

在常见 64 位平台假设：

* `A(double)=8`
* `A(int)=4`
* `A(char)=1`

推导结果：

* `A(S)=max(8,4,1)=8`
* 布局通常是：

  * `a` 在 offset 0，占 8 字节
  * `b` 在 offset 8，占 4 字节（8 已满足 4 对齐）
  * `c` 在 offset 12，占 1 字节
  * 结构体总共用到 13 字节，为了让 `sizeof(S)` 成为 8 的倍数，末尾补 padding 到 16

因此常见结果是：

* `alignof(struct S) == 8`
* `sizeof(struct S) == 16`

---

## 6. 硬件 → ABI → 编译器：规则从哪里来？

可以用一条链路理解对齐规则如何“产生并固化”：

1. **硬件（CPU/内存系统）**
   对齐访问更快、更简单，有的架构对未对齐访问代价高甚至不允许。

2. **ABI（应用二进制接口）**
   为了让不同编译器生成的二进制能互相调用、共享库能工作，ABI 会规定：

   * 各基本类型的大小与对齐
   * 结构体字段如何排布
   * 结构体对齐取最大成员对齐
   * `sizeof(struct)` 对齐倍数补齐（便于数组）

3. **编译器实现 C 语言布局**
   编译器按 ABI 规则插 padding、计算字段偏移、确定 `alignof/sizeof`，并保证数组、嵌套等场景仍然对齐正确。

## 7. 如何在代码里验证（推荐）

C11 可以直接打印对齐和偏移：

```c
#include <stdio.h>
#include <stddef.h>
#include <stdalign.h>

struct S { double a; int b; char c; };

int main() {
  printf("alignof(S)=%zu sizeof(S)=%zu\n", alignof(struct S), sizeof(struct S));
  printf("offsetof(a)=%zu offsetof(b)=%zu offsetof(c)=%zu\n",
         offsetof(struct S,a), offsetof(struct S,b), offsetof(struct S,c));
}
```

---

## 8. 一句话总结（便于记忆）

* **成员按自己对齐放**（不够就插 padding）
* **struct 的对齐 = 最大成员对齐**
* **sizeof(struct) 补到 struct 对齐的整数倍（保证数组里每个元素也对齐）**
* 这些规则背后来自：**硬件偏好/限制 → ABI 固化 → 编译器遵守实现**
