# I/O 多路复用技术深度解析

—— select / poll / epoll 原理、实现与工程实践

---

## 一、I/O 多路复用的背景与动机

### 1.1 为什么需要 I/O 多路复用？

在网络服务器中，核心问题是：

> **如何高效地同时处理大量客户端连接？**

传统方案存在明显缺陷：

### 1️⃣ 多进程 / 多线程模型

* 每个客户端一个进程或线程
* 优点：逻辑简单
* 缺点：

  * 进程 / 线程创建成本高
  * 上下文切换频繁
  * 内存消耗大
* 适合：连接数少、业务复杂

### 2️⃣ 非阻塞轮询模型

* 单进程反复轮询所有 socket
* 问题：

  * CPU 忙等待（100% 占用）
  * 即使无数据也不断检查
* 本质问题：**无效工作过多**

---

### 1.2 I/O 多路复用的核心思想

> **把“等待 I/O 就绪”的工作交给操作系统完成**

* 应用程序：

  * 告诉内核：我要关心哪些 fd
* 操作系统：

  * 负责监控这些 fd
  * 当某个 fd 就绪时唤醒应用程序

📌 **I/O 多路复用本身并不进行 I/O**
📌 **真正读写仍由 read / write 完成**

---

## 二、select 机制深度解析

### 2.1 select 的基本工作流程

一次完整的 select 调用过程：

1. 用户态准备 fd_set（位图）
2. 调用 select()
3. 内核：

   * 拷贝 fd_set
   * 线性扫描所有 fd
   * 判断是否就绪
4. 内核修改 fd_set，仅保留就绪 fd
5. 返回用户态
6. 用户再次遍历 fd_set 处理就绪 fd

---

### 2.2 fd_set 的本质

```c
typedef struct {
    unsigned long fds_bits[__FDSET_LONGS];
} fd_set;
```

* 位图结构
* fd 对应一个 bit
* FD_SETSIZE 通常为 **1024**
* fd 值越大，扫描成本越高

---

### 2.3 select 的触发模式：条件触发（LT）

**条件触发（Level Triggered）含义：**

> 只要当前状态满足条件（如缓冲区非空），就会不断通知

示例：

* 客户端发送 100 字节
* 服务器一次读 20 字节
* 剩余 80 字节仍在缓冲区
* 下次 select 仍然返回“可读”

📌 **LT 不会丢事件，但可能重复通知**

---

### 2.4 select 的主要缺陷

| 缺陷      | 本质原因           |
| ------- | -------------- |
| fd 数量限制 | 位图大小固定         |
| 性能低     | 每次 O(n) 扫描     |
| 内存拷贝    | 每次调用复制 fd_set  |
| 编程繁琐    | fd_set 被修改，需重置 |

---

## 三、poll 机制解析

### 3.1 poll 的设计改进

poll 主要解决了 select 的两个问题：

* ❌ fd 数量上限
* ❌ fd_set 位图不灵活

```c
struct pollfd {
    int   fd;
    short events;
    short revents;
};
```

* events：关心的事件
* revents：实际发生的事件
* 不再需要每次重建结构

---

### 3.2 poll 的性能瓶颈

尽管 poll 更灵活，但：

* 每次调用仍需传递整个数组
* 内核仍需线性扫描
* 时间复杂度仍是 **O(n)**

📌 **poll 解决“能不能用”，但没解决“快不快”**

---

## 四、epoll：高并发的真正解决方案

### 4.1 epoll 的设计理念

> **不要每次告诉内核“我关心谁”，
> 只要让内核在“有人出事时通知我”**

---

### 4.2 epoll 的三个核心接口

1️⃣ `epoll_create`

* 创建 epoll 实例
* 内核分配数据结构

2️⃣ `epoll_ctl`

* 添加 / 修改 / 删除监控的 fd
* fd 被加入内核红黑树

3️⃣ `epoll_wait`

* 等待事件发生
* **只返回就绪的 fd**

---

### 4.3 epoll 的内核数据结构

| 结构   | 作用         |
| ---- | ---------- |
| 红黑树  | 管理所有监控 fd  |
| 就绪链表 | 存放发生事件的 fd |
| 回调函数 | fd 状态变化时触发 |

📌 **epoll 不再扫描所有 fd**

---

### 4.4 epoll 的两种触发模式

#### 4.4.1 条件触发（LT）

* 默认模式
* 行为与 select / poll 相同
* 编程简单、安全

#### 4.4.2 边缘触发（ET）

* 仅在状态变化时通知一次
* 要求：

  * 非阻塞 socket
  * 一次性读空缓冲区

📌 **ET = 高性能 + 高风险**

---

### 4.5 ET 模式的正确使用方式

```c
while (1) {
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n > 0) {
        handle();
    } else if (n == 0) {
        close(fd);
        break;
    } else {
        if (errno == EAGAIN || errno == EWOULDBLOCK)
            break;
        else
            error();
    }
}
```

---

## 五、三种机制的本质对比

| 维度    | select | poll | epoll   |
| ----- | ------ | ---- | ------- |
| fd 传递 | 每次     | 每次   | 一次      |
| 内核扫描  | O(n)   | O(n) | O(1)    |
| 内存拷贝  | 多      | 多    | 极少      |
| 触发模式  | LT     | LT   | LT / ET |
| 并发能力  | 低      | 中    | 高       |
| 平台    | 跨平台    | 跨平台  | Linux   |

---

## 六、select / poll / epoll 的适用场景

### 使用 select：

* fd 数量少（<1024）
* 跨平台
* 教学 / 原型程序

### 使用 poll：

* fd 数量中等
* 不依赖 Linux 特性

### 使用 epoll：

* 高并发服务器
* Linux 平台
* 性能敏感系统（Web / Redis / Nginx）

---

## 七、条件触发 vs 边缘触发（核心对比）

| 项目      | LT | ET |
| ------- | -- | -- |
| 通知次数    | 多  | 少  |
| 编程难度    | 低  | 高  |
| 是否可能丢事件 | 否  | 是  |
| 性能      | 中  | 高  |

📌 **ET 必须配合非阻塞 I/O 使用**

---

## 八、现代演进与展望

### 8.1 epoll 仍然不是终点

* epoll 本质仍是同步 I/O
* 用户态仍需主动 read / write

### 8.2 io_uring（未来趋势）

| epoll  | io_uring |
| ------ | -------- |
| 事件通知   | 真正异步     |
| 多次系统调用 | 少量甚至无    |
| 性能     | 更高       |

---

## 九、核心总结（可直接背）

> * I/O 多路复用的本质是“让内核替你等待”
> * select / poll = 内核看完，你自己找
> * epoll = 内核直接告诉你谁就绪
> * LT 安全但重复，ET 高效但危险
> * 高并发的关键不是线程多，而是无效工作少
