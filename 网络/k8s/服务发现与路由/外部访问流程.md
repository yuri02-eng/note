# 1. 外部请求进 Pod 的大图（总览）

从“外部用户”到“Pod 容器”的典型路径可以概括成：

* L4 入口：

  * 外部 → **LoadBalancer / NodePort** → Node → **Service(ClusterIP)** → Pod
  
    ```javascript
    Client --> (DNS 解析到 NodeIP)
    Client --> NodeIP:NodePort  (入口：任一节点)
      -> kube-proxy (iptables/ipvs/eBPF)：命中 Service VIP 规则、挑后端 Pod
        -> 若同节点：DNAT 到 PodIP，直接本地转发
        -> 若跨节点：走 CNI 路由（VXLAN/IPIP/BGP）到目标节点，再入 Pod
      -> Pod -> 容器业务进程
      <- 原路返回（可能 SNAT 到 NodeIP；受 externalTrafficPolicy 影响）
    ```
  
    云上L4转发
  
    ```javascript
    Client --> (公共DNS -> LB 公网IP)
    Client --> 云LB(四层)  --健康检查-->
      -> LB 转发到某个 NodeIP:NodePort（会避开无后端的节点）
        -> 节点内 kube-proxy/内核：挑选 Service 后端 Pod（EndpointSlice）
          -> 同节点 or 跨节点（CNI）
      -> Pod
    ```
  
* L7 入口：

  * 外部 → **Ingress/Gateway(LB)** → Ingress Controller → **Service(ClusterIP)** → Pod

```javascript
Client --> (DNS -> Ingress/网关的 LB 公网IP)
Client --> LB(L4) --> Ingress Controller Pod(Nginx/Traefik/Istio Gateway)
  -> Ingress 规则：Host/Path/TLS 终止、重写、WAF、限流、金丝雀等（L7 功能）
  -> 选择目标 Service:Port
    -> kube-proxy/eBPF 挑后端 Pod（EndpointSlice）
      -> 同节点 or 跨节点（CNI）
  -> 目标 Pod
```

“Ingress Controller 不会像普通 Pod 那样用 DNS 去解析 `user-service.ns.svc.cluster.local`域名，它是直接 watch Kubernetes API，**根据 Ingress 里引用的 Service 去拿 Service 和 EndpointSlice，得到后端 Pod 列表。**

在数据平面上，有两种常见实现：

- 一种是把 Service 的 **ClusterIP:Port** 配成 upstream，这样流量还是会经过 kube-proxy 或 eBPF 的四层负载；

  ```javascript
  Client
    -> Ingress LB (L4)
    -> Ingress Controller (L7：Host/Path/TLS)
       -> Service ClusterIP:Port (10.96.123.45:80)
          -> kube-proxy/eBPF（L4 负载）
             -> PodIP:targetPort (10.244.x.x:8080)
  ```

  

- 另一种是直接用 Endpoint 里的 **PodIP:targetPort** 做 upstream，这样 Ingress 就自己实现了 L7 + L4 的负载均衡，相当于绕过了 Service 的 ClusterIP 和 kube-proxy，直接经 CNI 路由到 Pod。

  ```javascript
  Client
    -> Ingress LB (L4)
    -> Ingress Controller (L7 + 自己 L4)
       -> 直接 PodIP:targetPort（通过 CNI 路由）
  ```

对 NGINX Ingress：在 Ingress 上加 `nginx.ingress.kubernetes.io/service-upstream: "true"`。

这样路径变成：`Client -> Ingress(L7) -> Service(ClusterIP,L4) -> kube-proxy/eBPF -> Pod`。

所以，**控制面一定是 API 拿 Endpoint，不用 DNS；数据面是不是绕过 Service/kube-proxy，要看具体 Ingress 实现和配置。**”

核心统一逻辑是：

> **所有普通 Service 都是通过一个虚拟 IP（ClusterIP） + kube-proxy/eBPF，在节点内核里做四层负载均衡，把流量分发到 Pod。**

# 2. Service & ClusterIP 虚拟 IP 的作用

Service 其实就是：**稳定的服务端点 + 集群内四层负载均衡**。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: user-service
spec:
  selector:
    app: user
  ports:
  - port: 80         # Service 暴露的稳定端口
    targetPort: 8080 # Pod 实际监听端口
  clusterIP: 10.96.123.45  # 虚拟 IP（ClusterIP）
```

虚拟 IP 的核心价值：

1. **服务发现**：
   Pod 会重建 / IP 会变，但 `user-service:80` / `10.96.123.45:80` 不变。
2. **负载均衡**：
   在多个后端 Pod 之间分流（基于 Endpoints / EndpointSlice）。
3. **解耦**：
   调用方只认 Service，不关心后端 Pod 长啥样。

# 3. 情况 A：普通 Service（有 ClusterIP）的完整流程

目标：
`svc.ns.svc.cluster.local:Port` → `PodIP:targetPort`

### 3.1 DNS 解析（只到 Service VIP）

* 应用访问：`http://user-service/api` 或 `http://user-service.ns.svc.cluster.local`
* CoreDNS 解析：

  ```txt
  A user-service.ns.svc.cluster.local = 10.96.123.45    # Service 的 ClusterIP
  ```
* （可选） SRV 记录会把端口名映射到端口号
* 应用最终向：`10.96.123.45:80` 发起 TCP/UDP 连接
  👉 **此时完全还不知道 PodIP，DNS 只管到 ClusterIP。**

### 3.2 数据包进入节点内核

* 客户端（Pod 内或外部）发包目标：`dst=10.96.123.45:80`
* 包进入某个节点的内核网络栈（本机节点 / 入口节点）

### 3.3 在节点内核里：kube-proxy / eBPF 选 Pod & DNAT（关键）

**kube-proxy**（或 Cilium 之类的 eBPF）提前把 Service & EndpointSlice 转成本机规则：

* iptables 模式：KUBE-SERVICES / KUBE-SVC-* / KUBE-SEP-* 链
* ipvs 模式：内核 IPVS 表（rr、lc 等调度算法）
* eBPF：BPF maps + 程序挂在 tc/xdp 钩子

当包命中 Service 对应的 VIP + 端口时：

1. 匹配到该 Service 的规则链
2. 根据 **EndpointSlice** 中的 Pod 列表，结合：就绪状态、local/zone 拓扑、权重等选一个后端
3. 做 **DNAT**：

   ```txt
   10.96.123.45:80  →  10.244.1.2:8080   # 举例
   ```

   其中 `targetPort` 既可以是数字，也可以是**端口名**，会按 Pod 里容器定义解析成具体端口号。
4. 再按照路由把包发给这个 PodIP：

   * 同节点：直接走 veth / cni0 到 Pod
   * 跨节点：通过 CNI（VXLAN/IPIP/BGP/直连）到目标节点

> ✅ 所以你问的：**“DNS 解析后发送这个数据包，发送出去的时候，是不是在内核选择合适 Pod？”**
> 答案就是：**是的**，具体就是在节点内核里，由 kube-proxy/eBPF 挂的规则完成 Pod 的选择和 DNAT。

### 3.4 SNAT 与 externalTrafficPolicy

对于来自集群外的流量：

* `externalTrafficPolicy: Cluster`（默认）：

  * kube-proxy 通常会 **SNAT** 成节点 IP；Pod 看到的源是 NodeIP。
* `externalTrafficPolicy: Local`：

  * 只选本节点上有后端 Pod 的节点，不做 SNAT，可以保留客户端源 IP（配合 LB 的 `healthCheckNodePort`）。

# 4. 情况 B：Headless Service（`clusterIP: None`）

目标：
`svc.ns.svc.cluster.local:Port` → **直接 PodIP:targetPort**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: headless-svc
spec:
  clusterIP: None
  selector:
    app: db
  ports:
  - name: mysql
    port: 3306
    targetPort: 3306
```

* DNS 解析时，CoreDNS 直接返回**所有后端 Pod 的 A 记录**：

  ```txt
  A headless-svc.ns.svc.cluster.local = 10.244.1.2, 10.244.2.3, ...
  ```
* 客户端自己从这些 PodIP 中选择一个（一般是轮询）
* 然后直接连接 **`PodIP:targetPort`**
  👉 这条路径**不再经过 ClusterIP，也不需要 kube-proxy 做 DNAT**，常用于数据库、有状态组件内部发现等。

# 5. Service 虚拟 IP 的转发时机（更细一点）

你贴的伪代码可以这样理解：

1. 数据包进入节点内核时：

   * 内核看：目标 IP 是不是某个 Service VIP（ClusterIP）
   * 如果是，就按照 kube-proxy 填好的 iptables/ipvs/eBPF 规则走：

   ```go
   if packet.destIP == serviceVIP {
       // 在 KUBE-SERVICES / IPVS / BPF map 找到后端列表
       newDest := selectPodFromEndpoints(service)
       // 做 DNAT
       packet.destIP   = newDest.ip
       packet.destPort = newDest.port
       // 按路由发往 Pod
   }
   ```

2. kube-proxy 一直在 watch API：

   * `Endpoints / EndpointSlice` 一有变化（Pod 增删、就绪变化等）
   * kube-proxy 就 **刷新本地 iptables / ipvs / BPF 表项**

# 6. 不同访问路径的对比（把外部入口也串起来）

### 6.1 内部 Pod ↔ Service（ClusterIP）

```txt
PodA -> user-service:80
  DNS: user-service -> 10.96.123.45
  内核：ClusterIP:80 -> (DNAT) -> PodIP:8080
```

### 6.2 外部 ↔ NodePort

```txt
外部 Client -> NodeIP:NodePort
  Node 上 kube-proxy：NodePort -> 对应 Service (ClusterIP) -> 后端 Pod
```

### 6.3 外部 ↔ LoadBalancer

```txt
Client -> LB 公网 IP
  LB (L4) -> 某 NodeIP:NodePort
    Node 内核：NodePort -> Service ClusterIP -> PodIP
```

### 6.4 外部 ↔ Ingress（L7）

```txt
Client -> Ingress LB 公网 IP
  LB (L4) -> Ingress Controller Pod
    Ingress (L7) ：按 Host/Path/TLS 选一个 Service:Port
      -> Service (ClusterIP) -> 内核 DNAT -> PodIP:targetPort
```

# 7. Endpoint / EndpointSlice（后端列表）

传统 `Endpoints`（旧 API）：

```yaml
apiVersion: v1
kind: Endpoints
metadata:
  name: user-service
subsets:
- addresses:
  - ip: 10.244.1.2
  - ip: 10.244.2.3
  ports:
  - port: 8080
```

现代 `EndpointSlice`（新 API，性能更好）：

```yaml
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  name: user-service-abc123
  labels:
    kubernetes.io/service-name: user-service
addressType: IPv4
ports:
- name: http
  protocol: TCP
  port: 8080
endpoints:
- addresses: ["10.244.1.2"]
  conditions: { ready: true }
- addresses: ["10.244.2.3"]
  conditions: { ready: true }
```

kube-proxy / Cilium 等就是根据这些 EndpointSlice 来构建本地的负载均衡表的。

# 8. 为什么一定要有 Service / 虚拟 IP？

没有 Service：

* Pod IP 是**动态**的，重建就变，应用连 `10.244.1.2:8080` 很快就失效。
* 你必须自己维护：

  * Pod 列表
  * 健康检查
  * 负载均衡算法
    ——又麻烦又容易出错。

有 Service：

* 应用只写：`http://user-service:80`
* Kubernetes 保证：

  * 名字 → ClusterIP（CoreDNS）
  * ClusterIP → 健康 Pod 列表（EndpointSlice）
  * 节点内核里按策略分流（iptables/ipvs/eBPF）

# 9. 常用排查命令（真上机/面试问排障时好用）

```bash
# 看 Service 和 ClusterIP
kubectl get svc user-service -o wide

# 看 EndpointSlice 实际后端
kubectl get endpointslice -l kubernetes.io/service-name=user-service -o wide

# 看 iptables 规则（iptables 模式）
iptables-save -t nat | grep KUBE-SVC | grep USER

# IPVS 模式
ipvsadm -Ln

# eBPF / Cilium
cilium service list
cilium bpf lb list

# DNS 解析情况
kubectl exec -it <pod> -- nslookup user-service
dig A user-service.ns.svc.cluster.local
```

# 10. 面试总结话术

> “普通 Service 的访问流程是：应用通过 DNS 把服务名解析到一个 ClusterIP，发包到这个 VIP。真正决定哪个 Pod 收包，不是在 DNS，而是在每个节点的内核里。kube-proxy（iptables/ipvs）或 eBPF 根据 EndpointSlice 里的后端 Pod 列表，在内核态把目标地址从 ClusterIP:Port DNAT 成某个 PodIP:targetPort，再由 CNI 负责跨节点路由。Headless Service 则直接把 PodIP 列给客户端，客户端自己挑，这时候就不再走 ClusterIP 和 kube-proxy 了。”

这基本把你问的“DNS → ClusterIP → 选 Pod → DNAT”这条链路说全了，也能和「外部请求进入集群」那道面试题合在一起用。
