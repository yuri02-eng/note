# 一、整体概念：服务发现与路由

![服务访问流程](E:\笔记\网络\k8s\服务访问流程.png)

在 Kubernetes 中，Pod IP 是**短暂**的（重建就变），集群需要一种方式让服务之间、以及外部客户端能**稳定、可靠地访问后端 Pod**。

核心问题有两个：

1. **服务发现（Service Discovery）**

   * 客户端如何找到服务？（通过固定名称 + 虚拟 IP + DNS）
2. **路由（Routing）**

   * 请求进来后，如何在不同节点、不同 Pod、不同拓扑之间做转发和负载均衡？

K8s 提供的主要构件：

* Service（ClusterIP / NodePort / LoadBalancer / ExternalName / Headless）
* 拓扑感知路由（Topology Aware Routing）
* Ingress
* Gateway API（以及扩展与迁移）

---

# 二、Service

Service 是一个**稳定的访问入口**，通过 label selector 选中一组 Pod，对外暴露为一个固定的虚拟 IP + 端口。

## 1. 为什么需要 Service？

* Pod 重建 → IP 改变
* 客户端不可能一直追踪 Pod IP
* Service 提供：

  * **稳定的 DNS 名称**：`my-svc.my-namespace.svc.cluster.local`
  * **虚拟 IP（ClusterIP）**：由 kube-proxy + iptables/ipvs 实现负载均衡

## 2. 常见类型

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app
  ports:
  - port: 80        # Service 暴露的端口
    targetPort: 8080  # Pod 容器端口
```

1. **ClusterIP（默认）**

   * 只在集群内部访问
   * 用于服务间调用（微服务内部通信）

2. **NodePort**

   * 在每个节点上开一个端口（`nodePort`）
   * 外部请求：`NodeIP:nodePort -> Service -> Pod`
   * 常用于测试或自管理外部 LB 的场景

3. **LoadBalancer**

   * 在云环境中创建云厂商的 LB（如 ELB / SLB）
   * 外部直接访问云 LB 的 IP / 域名
   * 适合对外公开服务

4. **ExternalName**

   * 不进行负载均衡，只是把 Service 名称映射到外部 DNS 名称
   * 常用于访问外部数据库、第三方服务

   ```yaml
   apiVersion: v1
   kind: Service
   metadata:
     name: external-db
   spec:
     type: ExternalName
     externalName: db.example.com
   ```

5. **Headless Service（无头 Service）**

   * `spec.clusterIP: None`
   * 不分配虚拟 IP，DNS 直接返回所有 Pod 的 IP
   * 应用自己做负载均衡/分片
   * 常配合 StatefulSet，用在数据库、消息队列等有状态服务里

# 三、拓扑感知路由（Topology Aware Routing）

目的：**尽量就近访问**，减少跨机架 / 跨可用区的流量，提高性能并降低费用。

核心思想：

* Kubernetes 根据 **节点拓扑标签**（如 `topology.kubernetes.io/zone`、`region` 等）
* 优先把流量转发到与客户端在**同一拓扑域**（同节点 / 同 Zone）的后端 Pod
* 当本地没有足够 Pod 时，再跨拓扑转发

使用方式（示意）：

* 开启 `Service` 的拓扑感知特性（具体开关取决于版本和集群配置）
* 保证节点打上正确的拓扑标签
* 对上层应用透明：客户端仍然通过 Service 访问，K8s 在后面做“就近路由”

适用场景：

* 多可用区部署（Multi-AZ）
* 跨地区成本敏感的流量
* 对延迟比较敏感的服务

# 四、Ingress

**Ingress = L7（HTTP/HTTPS）反向代理 + 路由规则**。

它解决的问题是：**如何用一个（或少数几个）入口 IP / 域名，访问集群内的多个 Service**。

## 1. 组件关系

* **Ingress 资源**：只是一堆路由规则（YAML 配置）
* **Ingress Controller**：真正干活的控制器（nginx、traefik、kong、istio 等）

  * 监听 Ingress 对象的变化
  * 生成并应用对应的代理配置

## 2. 功能

* 基于 **Host** 和 **Path** 的路由：

  * `foo.example.com` → service-a
  * `bar.example.com/api` → service-b
* TLS 终止（HTTPS）
* 基础的重定向、重写、限流（视具体 Controller 而定）

## 3. 示例

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
spec:
  rules:
  - host: example.com
    http:
      paths:
      - path: /app
        pathType: Prefix
        backend:
          service:
            name: my-service
            port:
              number: 80
```

## 4. 与 Service 的关系

* **Service：稳定访问一组 Pod（L4）**
* **Ingress：将外部 HTTP/HTTPS 流量路由到一个或多个 Service（L7）**
* 通常：`Client -> LB / NodePort -> Ingress Controller -> Service -> Pod`

# 五、Gateway API

Gateway API 是 Kubernetes 网络的**下一代抽象**，由 SIG-Network 维护，目标是替代 / 增强 Ingress。

## 1. 设计目标

* 比 Ingress **更通用、更可扩展**
* 支持多种协议：HTTP、TCP、TLS、gRPC 等
* 更清晰的职责分离：基础设施团队 / 平台团队 / 应用团队各自管理不同资源
* 更好地表达高级流量管理需求（流量拆分、灰度、策略等）

## 2. 核心资源

常见几个对象：

1. **GatewayClass**

   * 类似于“入口实现类型”
   * 由平台/运维定义：比如 `nginx`, `istio`, `haproxy` 等实现

2. **Gateway**

   * 实际的网络入口（对应一组 IP / 端口 / 证书）
   * 由基础设施团队创建、控制

3. **Route 系列（如 HTTPRoute、TCPRoute、TLSRoute、GRPCRoute）**

   * 定义具体的路由规则和后端 Service
   * 多个团队可以在同一个 Gateway 上绑定自己的 Route（多租户）

4. **ReferenceGrant 等**

   * 解决跨命名空间引用的授权问题

## 3. 简单示例（HTTPRoute）

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: my-gateway
spec:
  gatewayClassName: nginx
  listeners:
  - name: http
    protocol: HTTP
    port: 80
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-route
spec:
  parentRefs:
  - name: my-gateway
  rules:
  - matches:
    - path:
        type: PathPrefix
        value: /app
    backendRefs:
    - name: my-service
      port: 80
```

对比 Ingress：

* Ingress：所有配置写在一个对象里，扩展能力有限
* Gateway API：入口（Gateway）与路由（HTTPRoute 等）分离，更易于多团队协作和扩展

# 六、Gateway API 推理 / 扩展（实验性与扩展能力）

文档中这块通常讲的是 **Gateway API 的扩展与实验性功能**，大致包括：

1. **更多的 Route 类型**

   * `GRPCRoute`：针对 gRPC 协议的路由
   * `TCPRoute` / `UDPRoute`：四层协议
   * `TLSRoute`：更细粒度的 TLS 流量控制

2. **策略（Policy）扩展**

   * 通过单独的 Policy 对象给 Gateway / Route / Backend 附加策略，例如：

     * 超时、重试
     * 头部注入 / 修改
     * 访问控制、安全策略
   * 常见模式是“Policy Attachment”：不同 CRD 通过 `targetRef` 绑定到 Gateway/Route

3. **供应商/实现扩展**

   * 各家 Ingress/Gateway 实现可以提供自定义扩展字段，而不破坏标准 API
   * 比如 Nginx/Envoy 特有的高级功能

理解要点：
👉 Gateway API 并不是一个单一控制器，而是一套 **可扩展的标准 API**，具体功能取决于你使用的实现（nginx、istio、kong 等）。

# 七、迁移到 Gateway API

文档中这部分主要讲 **从传统 Ingress/Service 迁移到 Gateway API 的思路**。

常见迁移步骤：

1. **梳理现有 Ingress 规则**

   * 域名、路径、TLS、重写、头部等
2. **创建 GatewayClass & Gateway**

   * 选择对应实现（如 nginx-gateway、istio 等）
   * 规划监听端口、TLS 证书、负载均衡方式
3. **将 Ingress 规则拆分为 HTTPRoute 等对象**

   * `host/path` 映射 → `HTTPRoute.rules.matches`
   * 后端 Service → `backendRefs`
   * TLS 配置 → Gateway 的 `listeners` + 证书引用
4. **逐步切流 / 双栈运行**

   * 同时运行旧 Ingress 与新 Gateway
   * 通过 DNS 或 LB 配置渐进迁移流量
5. **删除旧 Ingress 配置**

   * 监控、验证无误后，下线旧 Ingress Controller

迁移好处：

* 更清晰的责任边界（平台团队管 Gateway，业务团队管 Route）
* 更丰富的流量管理能力
* 与社区未来发展保持一致（Gateway API 是官方推荐方向
