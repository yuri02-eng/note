# select / epoll 面试高频问答（系统整理版）

---

## 一、基础认知类（必问）

---

### 1️⃣ 什么是 I/O 多路复用？

**一句话回答：**
I/O 多路复用是一种机制，允许一个进程或线程同时监视多个文件描述符，由操作系统在 I/O 就绪时通知应用程序。

**展开解释：**
应用程序将多个 fd 注册给内核，内核负责等待这些 fd 的 I/O 事件，当某个 fd 可读、可写或异常时，唤醒应用程序进行处理。

**面试加分点：**

* I/O 多路复用本身不做 I/O
* 真正的数据读写仍然由 read / write 完成

---

### 2️⃣ select、poll、epoll 的本质区别是什么？

**一句话回答：**
本质区别在于**内核如何保存和返回“就绪的文件描述符”**。

**展开解释：**

| 机制     | 核心差异              |
| ------ | ----------------- |
| select | 每次传递 fd 集合，内核线性扫描 |
| poll   | 数组形式传递，仍线性扫描      |
| epoll  | fd 注册一次，内核事件驱动    |

**加分点：**
epoll 通过回调机制和就绪链表避免了无效扫描。

---

### 3️⃣ select 的最大缺点是什么？

**一句话回答：**
select 的最大缺点是性能随 fd 数量线性下降，并且存在 fd 数量上限。

**展开解释：**

* fd 数量限制（通常 1024）
* 每次调用 O(n) 扫描
* 每次调用都需要拷贝 fd_set
* fd_set 会被修改，需要重置

**加分点：**
select 在 fd 数量很少时仍然适用。

---

## 二、epoll 原理类（高频重点）

---

### 4️⃣ epoll 为什么比 select 快？

**一句话回答：**
因为 epoll 不再每次扫描所有 fd，而是只处理真正就绪的 fd。

**展开解释：**

* epoll_ctl 注册 fd 到内核
* 内核维护就绪链表
* epoll_wait 只返回活跃 fd

**加分点：**
epoll 的时间复杂度接近 O(1 + k)，k 是活跃 fd 数量。

---

### 5️⃣ epoll 的 LT 和 ET 模式有什么区别？

**一句话回答：**
LT 是“只要条件满足就通知”，ET 是“只在状态变化时通知”。

**展开解释：**

| 模式 | 行为         |
| -- | ---------- |
| LT | 缓冲区非空就一直通知 |
| ET | 从空到非空只通知一次 |

**加分点：**
ET 模式显著减少系统调用次数，但编程更复杂。

---

### 6️⃣ 为什么 ET 模式必须使用非阻塞 I/O？

**一句话回答：**
因为 ET 只通知一次，如果阻塞读会导致事件丢失或死锁。

**展开解释：**

* ET 不会反复通知
* 阻塞 read 可能卡死事件循环
* 非阻塞 + 循环读到 EAGAIN 是标准写法

**加分点：**
这是 ET 最常见的面试陷阱。

---

### 7️⃣ epoll 会不会丢事件？

**一句话回答：**
LT 不会丢事件，ET 在编程不当时可能丢事件。

**展开解释：**

* ET 若未一次性读空缓冲区
* 后续不会再收到通知
* 数据“逻辑上丢失”

**加分点：**
内核数据没丢，丢的是应用层感知。

---

## 三、对比与设计思想类（中高级）

---

### 8️⃣ poll 相比 select 有什么改进？

**一句话回答：**
poll 去掉了 fd 数量限制，并简化了事件管理。

**展开解释：**

* 使用 pollfd 数组
* events / revents 分离
* 不再依赖位图

**加分点：**
poll 仍然是 O(n)，性能和 select 本质一致。

---

### 9️⃣ epoll 的内核数据结构有哪些？

**一句话回答：**
epoll 主要使用红黑树和就绪链表。

**展开解释：**

* 红黑树存储所有监控 fd
* 就绪链表存储发生事件的 fd
* 回调函数触发事件入队

**加分点：**
就绪链表避免全量扫描。

---

### 🔟 为什么 select / poll 每次都要传 fd？

**一句话回答：**
因为内核不会长期保存监控集合，只能通过系统调用传递。

**展开解释：**

* select / poll 是“无状态”的
* epoll 是“有状态”的

**加分点：**
这是三者设计哲学的根本差异。

## 四、实战与陷阱类（面试加分）

---

### 1️⃣1️⃣ epoll 的惊群效应是什么？如何解决？

**一句话回答：**
多个线程/进程同时被唤醒抢同一事件。

**解决方式：**

* EPOLLEXCLUSIVE
* SO_REUSEPORT
* 单线程 epoll + 工作线程池

---

### 1️⃣2️⃣ select / epoll 中的“可读”具体指什么？

**一句话回答：**
表示 read 不会阻塞。

**展开解释：**

* 接收缓冲区非空
* 对端关闭（EOF）
* 错误条件

---

### 1️⃣3️⃣ epoll 和多线程可以一起用吗？

**一句话回答：**
可以，但要谨慎设计。

**展开解释：**

* 常见模型：1 epoll 线程 + N worker
* 避免多个线程同时 epoll_wait 同一 epfd

**加分点：**
Nginx 使用单线程 epoll + 多进程模型。

---

### 1️⃣4️⃣ select 和 epoll 谁更省 CPU？

**一句话回答：**
epoll 更省 CPU，尤其在大量空闲连接时。

**原因：**

* select 扫描所有 fd
* epoll 只处理活跃 fd

---

## 五、总结型终极问答（压轴）

---

### 1️⃣5️⃣ 如果让你设计一个高并发服务器，你会怎么选？

**标准答案结构：**

1. Linux 平台
2. 高并发连接
3. 使用 epoll
4. ET + 非阻塞 I/O
5. 主线程 epoll_wait
6. 工作线程处理业务

**加分点：**

> 并发的核心不是“线程多”，而是“减少无效等待和扫描”。

---

## 六、一页速记版（面试前 5 分钟）

> * select/poll：每次扫描所有 fd
> * epoll：事件驱动，只处理活跃 fd
> * LT 安全，ET 高效
> * ET 必须非阻塞
> * epoll 是 Linux 高并发标配
